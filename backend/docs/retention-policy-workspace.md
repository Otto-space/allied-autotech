# Retention policy workspace

GET `/admin/policies/retention/current` returns evaluatedAt/current/nextScheduled/latest/history. Current and next are selected across all versions by effective time and descending version, independently from the latest 100 recorded history entries. Super Admin/MFA and current transaction actor/session checks protect a repeatable snapshot and atomic minimal RETENTION_POLICY_CURRENT READ audit. Responses are private/no-store. Existing bounded retries cover only database-aborted reads.

RETENTION publication now rechecks current actor/session under the organization access lock before existing policy-version locking, immutable APPROVED/Q13 creation and CREATE audit. The strict request contract is unchanged: destructiveExecutionEnabled must be false; 1–20 rules; categories ACCOUNT/PAYMENT/INVOICE/AUDIT/SUPPORT; whole months 1–1200; trimmed startEvent 5–200 characters; disposition RETAIN/REVIEW_ANONYMIZATION/REVIEW_DELETION; trimmed legalBasis 20–1000 characters. Source 10–500 characters, approvalEvidence 20–1000 characters, expected version and effective time retain existing checks. No schema or migration is required.

Publication does not delete/anonymize records, release holds or approve privacy requests. There is no enabled retention executor. Existing expiration/identity cleanup and privacy/hold review remain independent. The UI offers no destructive toggle, supplies no unapproved retention periods and requires written provenance. Legal-basis text records business approval; this implementation does not supply legal advice.

The frontend keeps draft structure/base through refresh and reload, validates exact nested settings and Q13/actor provenance, and preserves a minimal actor-bound uncertainty lock. Current-policy inspection plus independent reconciliation never replays a request or proves its original outcome.
