# Complaint policy workspace

The dedicated Super Admin page needs the effective policy independently of the latest 100 recorded versions. A newer version may take effect later; selecting history entry zero as current gives the wrong operational information.

`GET /api/v1/admin/policies/complaints/current` returns `evaluatedAt`, `current`, `latest`, `nextScheduled` and `history`. Current selection considers all complaint versions with effective time at or before the check, ordered by effective time descending then version descending. Next scheduled considers all future versions, ordered by effective time ascending then version descending. History retains the existing 100-version descending bound. Older draft/incomplete versions are returned truthfully; this read does not supply business approval.

The endpoint requires current active, verified Super Admin access and MFA. It rejects additional query parameters, uses `private, no-store`, checks the current user/session under the organization access lock, reads one repeatable snapshot and atomically appends a minimal `READ` audit with resource `COMPLAINT_POLICY_CURRENT` and returned history count. The existing bounded transaction helper retries only database-aborted serialization/deadlock transactions, accommodating concurrent authenticated session touches without duplicating committed read audits. It does not expose contact profiles in the policy response; the page resolves current account details through the existing authorized staff endpoint.

Existing `POST /admin/policies` complaint publication now takes the current actor/session lock and locks the selected contact row before eligibility checks. Existing approved version creation, optimistic `expectedVersion`, policy lock, Q11 provenance, effective-time validation, CSRF and atomic audit remain in force. Other policy kinds retain their existing behavior. Ordinary targets remain 600 accumulated working minutes, urgent targets 60 working minutes, Monday–Saturday 08:00–18:00 Lagos time with approved holiday exclusions. Existing complaint deadline snapshots are preserved.

The frontend rechecks its own profile, policy version and contact before sending. It validates the exact returned version, actor, Q11 provenance, settings and approval metadata. A minimal account-bound pending token, base version and body fingerprint lock uncertain submissions across reload. A fresh read plus independent reconciliation is required to clear the lock; a current policy is not proof of the earlier request's outcome.

## Verification and rollout

Local gate 94 is accepted; see the [complete report](../../frontend/docs/page-quality/work-complaint-policy.md). Six isolated API scenarios have passing assertion evidence across the original run and focused continuations. The original publication committed once; duplicate base-version publication returned 409. Test audit-field/status expectations were corrected, and continuation verified the retained publication without sending it again. Four rounds of concurrent profile/two-policy reads returned 200 with exactly eight policy READ audits and no publication. Initial and continuation preservation hashes cover 59 original users, 52 staff profiles, 13 policy versions, 375 audit rows and 38 branches, plus the empty complaint/payment/invoice/refund tables. Temporary sessions were removed. Test target: `127.0.0.1:55480/allied_work_staff_workforce_20261019_test`, environment `test`, restricted runtime credentials.

Connected production Edge/API/PostgreSQL verification confirms two future approvals and exactly two publication audits. The first successful receipt was followed by an intermittent refresh failure; its saved version was retained and verified without replay. The second deliberately lost response stayed locked after reload, required fresh inspection and independent reconciliation, and sent no extra publication. Continuation correlated five successful current-policy reads with five READ audits. All 116 pre-existing policy versions, 60 users, 53 staff profiles and empty complaint/financial tables stayed hash-unchanged; the current effective policy was unchanged and the temporary session was removed. Synthetic future approvals are test evidence, not business approval.

No schema/migration or grant change is required. Deploy backend, exported contracts and frontend together. No application/shared database, worker/provider, backup/restore, push or deployment operation ran for this gate. Existing migration replay and restricted-role evidence are reused because the schema and grants are unchanged; this is not a new restore rehearsal or proof of deployed recovery.

## Remaining backend improvement

There is no durable original-request publication receipt or authorized receipt lookup. If selected, bind a receipt to actor, operation, policy key, base version and canonical body; commit it atomically with the version and audit; enforce current access on lookup; define retention/expiry. Prove concurrent requests, mismatched bodies/actors, committed and uncommitted lost responses, and exactly one intended version/audit. Add any storage through the mandatory reviewed forward-migration workflow. The current UI does not pretend this capability exists.
