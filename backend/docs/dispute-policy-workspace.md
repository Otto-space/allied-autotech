# Dispute policy workspace

The Super Admin page distinguishes effective settings, the next scheduled version and the latest recorded version. GET `/admin/policies/disputes/current` returns `evaluatedAt`, `current`, `nextScheduled`, `latest` and at most 100 history entries. Selection examines all dispute policy versions using effective time then descending version; it does not infer current settings from the capped history. Current actor/session and MFA are checked in a repeatable-read transaction with an atomic minimal `DISPUTE_POLICY_CURRENT` READ audit and private/no-store response. Only database-aborted transactions are retried through the existing bounded helper.

POST `/admin/policies` retains the DISPUTES body, expected version and immutable APPROVED/Q9 provenance. It now obtains the organization access lock and rechecks the actor, then locks both selected accounts in stable UUID order. Both must remain distinct, active, verified Staff/Admin/Super Admin accounts with active DISPUTE_MANAGE grants. Capability changes use the same access lock. Existing version creation and CREATE audit remain atomic. No schema or migration is required; deploy the additive endpoint and generated contracts with the dependent frontend.

The frontend uses existing staff-directory search/cursors, direct account reads and active-grant reads. It repeats current identity/policy/contact/grant checks before sending, validates the exact returned actor, provenance, settings and effective time, and retains drafts with their base version. Refresh errors block writes. Unknown outcomes persist an actor-bound minimal lock; reading current settings does not prove the original outcome. Independent reconciliation is explicit and never replays the request.

## Operational boundary

Publication records defaults; it does not submit evidence, resolve a dispute or directly modify individual disputes. The operational-alert worker uses the effective policy to calculate an end-of-applicable-working-day acknowledgement deadline when one is missing. When the primary contact is absent it can supply both default contacts. Existing provider response deadlines remain authoritative. The redesign does not change worker execution, provider integrations or assignment rules.

## Remaining optional backend capability

There is no actor/operation/body-bound original-request receipt lookup for policy publication. If durable recovery is selected, define reference binding, retention/expiry and currently authorized read-only lookup; commit policy, audit and receipt atomically. Verify committed/uncommitted lost responses, concurrent requests, changed bodies, actor/session/grant changes and exactly one policy/audit. Deliver generated contracts and deliberate UI recovery together. Follow the mandatory forward-migration workflow if storage is added. Current frontend reconciliation is intentionally not proof of the earlier request.
