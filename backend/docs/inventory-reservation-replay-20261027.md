# Inventory reservation retry after expiry — 27 October 2026

An operator who lost the response to a successful reservation could not retry the same idempotency key after the requested expiry. The request schema rejected the expired timestamp before the service could compare the authorized original request and return the stored reservation. This made the unknown outcome harder to recover and could tempt a fresh reservation request.

The request schema still requires a valid offset datetime and matching reference fields. Inside the transaction, the service first locks the key, verifies current actor/branch access, and compares the existing reservation's request fingerprint and inventory. A matching retry returns the original reservation, including its current status, without extending its expiry or changing stock. Only a new key proceeds to the future/seven-day time-window check. An invalid new request returns `422 VALIDATION_FAILED` before any stock mutation; a reused key with different input remains `409 IDEMPOTENCY_CONFLICT`.

Verification on a freshly created loopback-only `aat_inventory_replay_*_ci` PostgreSQL database: all 74 migrations replayed with no Prisma schema difference, and the actual Phase 4 HTTP/inventory flow passed with expired replay and new-expired assertions. Three focused unit cases and four adjacent security cases passed; TypeScript, scoped lint/format and OpenAPI validation (365 paths) passed. The first isolated run reached the new assertions but later failed because its historical cart-clear fixture still sent an empty body. That fixture now sends the current reviewed cart snapshot; the final isolated run passed. Both task-created test containers used temporary storage and were removed. No application database, customer record, provider, payment or stock in production was touched.
