# Managed image lifecycle

BG-02 extends the existing S3 adapter, cookie sessions, CSRF middleware, audit events and general worker. The new `mediaStorage` adapter fails closed when storage is unavailable. It does not use the legacy synthetic fallback. Tests explicitly inject a byte-storing adapter; that is not a deployed-storage verification.

## Profile photo contract

Customer owners use `POST /customers/profile/photo/upload`, `PUT /customers/profile/photo` and `DELETE /customers/profile/photo`. Routes are under `/api/v1`. Admin, Super Admin and Staff cannot access personal photos. GET/PATCH profile responses include `mediaVersion` and nullable `photo`; existing metadata fields remain compatible. The frontend shows initials when no photo is attached.

Preparation accepts JPEG, PNG or WebP MIME type, actual byte count and lowercase SHA-256. Profile limits are 5 MiB, 32–8192 pixels per side, at most 40 million pixels and one non-animated image. Extreme aspect ratios that would shrink below 32 pixels are rejected. The server reads bounded bytes, verifies length/checksum/signature, fully decodes, rotates, resizes within 1024 pixels and re-encodes to WebP without source metadata. SVG, GIF, APNG, animated WebP and remote URLs are not accepted by this flow.

The random opaque token is stored only as a SHA-256 hash, bound to actor, owner, resource, purpose, branch, object, declared content and expiry. Upload keys are server-generated. Preparation returns a short-lived signed PUT credential only in the no-store preparation response. Uploading alone never changes the profile. Confirm uses the profile's `mediaVersion`, locks the ticket and profile, attaches the validated object, increments the media version and queues replaced objects in one transaction. Text-profile edits are independent. A failed transaction leaves the old photo attached and the unattached object eligible for cleanup.

Exact confirmation retries with the original body replay the stored safe result for 24 hours. Changed-body or later replays return `MEDIA_TICKET_CONSUMED`. The client rereads the profile after an uncertain response; it never creates another attachment to guess the outcome. Expired unconfirmed tokens cannot be confirmed. Stale mutations return `STALE_VERSION`. Removal is version-checked; uncertain removal requires rereading before another mutation.

Photos are served by `GET /customers/media/images/{imageId}` with owner authorization, `Cache-Control: private, no-store` and `X-Content-Type-Options: nosniff`. Cross-account IDs return 404. There is no public storage URL or signed download URL in profile projections. Removal revokes subsequent application reads at commit; already downloaded bytes cannot be revoked.

## Persistence and cleanup

Migration `20260930020000_managed_media_lifecycle` adds upload tickets, verified-asset metadata, resource-image references and durable cleanup jobs. It adds nullable references to existing catalogue/stock images without rewriting them. Private records hold no binary bytes. Database constraints enforce supported formats, valid resource binding, one profile/service image and at most one primary garage image.

The existing general worker runs `media-cleanup` on the expiration cadence, with an operations heartbeat. It claims bounded jobs, checks current managed and legacy image references before deletion, retries failures with backoff and stores only a safe failure code. Pending and unconfirmed verified keys are scheduled at upload expiry plus one hour, after signed PUT credentials expire. Replacement/removal queues the previous verified key immediately. Unreferenced assets left by cascaded resource deletion are discovered after one hour. A failed storage delete does not restore a removed application reference. Storage lifecycle rules must not independently delete referenced verified objects.

Successful preparation, replacement and removal use existing audit facilities with actor/resource/action/result. Request rejections use existing error logs; sensitive tokens, object keys and signed upload fields are redacted. Source filename and image metadata are never copied into audit values. Existing payment, booking, staff-role and deployment behavior is unchanged.

## Deployment verification still required

Configure a private bucket, region (default `us-east-1`), credentials or workload identity, and an endpoint for non-AWS S3 storage using the existing `OBJECT_STORAGE_*` variables. The API/worker identity needs GetObject, PutObject and DeleteObject on managed prefixes. Bucket CORS must allow the frontend origin's PUT and the signed content-type, checksum and encryption headers. Set frontend `ASSET_STORAGE_HOSTS` to the actual signed-upload hostname. Keep public access blocked. Run the normal migrations and general worker; do not use database reset or `db push`.

Live storage credentials/bucket are absent in this workspace. Before release, verify real signed PUT/checksum/SSE/CORS, confirm/read/replace/remove, expiry, storage outage, worker retries and private-bucket access denial in staging. No live-storage or staging pass is claimed by the local tests.

## BG-03: private garage galleries

The owner uses `POST /customers/vehicles/{vehicleId}/assets/upload`, `POST /customers/vehicles/{vehicleId}/images`, and `PATCH/DELETE /customers/vehicles/{vehicleId}/images/{imageId}`. GET vehicle detail returns `mediaVersion` and at most 12 safe image projections; existing metadata CRUD and list projections remain compatible. New media reuses migration 44 without another schema change.

Limits are 12 images, 10 MiB per image and WebP output within 2048 pixels, with the shared validation rules above. Images sort by `sortOrder` then image ID; equal sort numbers are deterministic. The first attachment is the cover. Selecting a cover requires `isPrimary: true`; the gallery cannot unset its only cover while images remain. Removing the cover chooses the first remaining image by the same ordering. An empty garage gallery is valid. Row locks, expected media versions and the partial unique primary index prevent lost updates and multiple covers. Existing metadata edits do not increment the media version.

Image reads use the same owner-only authenticated media endpoint as profile photos. Vehicle deletion locks the vehicle, removes image references by cascade and queues each verified object in the same transaction. Existing foreign-key restrictions still apply; a failed deletion rolls back cleanup scheduling. Garage media never enters public marketplace responses.

The vehicle list links to `/dashboard/vehicles/{vehicleId}`. The gallery has independent upload slots with previews, progress, cancellation and retry; already prepared files survive another file's confirmation. It supports alt text, numeric display order, cover selection and confirmed removal. After a successful write, controls remain disabled until the refreshed version arrives. Lost confirmation responses retain the original ticket/body for an exact retry.

## Service image checkpoint (BG-04)

Service image management uses the existing ADMIN/SUPER_ADMIN plus verified-MFA policy. STAFF and CUSTOMER are denied. The resource has one optional primary image, enforced by the existing managed-media migration's unique `ResourceImage.serviceId`; no additional migration is required.

| Method | Route                                                  | Result                                                        |
| ------ | ------------------------------------------------------ | ------------------------------------------------------------- |
| GET    | `/admin/services/{serviceId}/images`                   | Current service version and zero/one safe image               |
| POST   | `/admin/services/{serviceId}/assets/upload`            | Actor/service-bound upload ticket and signed PUT              |
| PUT    | `/admin/services/{serviceId}/image`                    | Verify and atomically replace image                           |
| PATCH  | `/admin/services/{serviceId}/images/{imageId}`         | Edit nullable alt text, up to 240 characters                  |
| DELETE | `/admin/services/{serviceId}/images/{imageId}`         | Detach image and queue object cleanup                         |
| GET    | `/admin/services/{serviceId}/images/{imageId}/content` | Authorized administrator preview, including inactive services |
| GET    | `/public/media/images/{imageId}`                       | Bytes only while the associated service is active             |

All writes require CSRF. Uploads use the shared JPEG/PNG/WebP validation, a 10 MiB byte limit and 2048px maximum output dimension. Tickets are purpose-, actor- and service-bound; prepare never publishes. Confirmation supports exact token/body replay for 24 hours. `expectedVersion` is the existing **Service.version**, shared with service metadata updates. Image changes take the same service advisory lock plus a row lock, and increment that version. Concurrent metadata/image writes cannot overwrite one another. Failed verification, stale confirmation or a failed transaction preserves the old image. Replacement/removal enqueue cleanup in the same transaction.

Public service list/detail responses add nullable `image` with ID, safe application URL, alt text, primary/order fields and dimensions. They contain no keys, tickets or signed credentials. Public image reads check `service.isActive` at request time, use `private, no-store` and `nosniff`, and never match customer profile/garage images. Inactive or detached public images return 404; existing service-deactivation rules are unchanged. Previously downloaded bytes cannot be revoked. Administrators preview inactive images through their separate authenticated content route.

The existing service management page opens a focused image editor and preserves the records page when closing it. Upload preview/progress/cancel/retry, confirmation, description editing, replacement and removal use the established frontend controls. Successful mutations wait for the refreshed version. Public cards and detail pages use responsive images; absent photos preserve their earlier presentation and failed image requests show a neutral service icon. OpenAPI and generated frontend types include all seven new operations.

A further HTTP assertion confirmed that the new public route cannot read a private profile image. OpenAPI validation covers 245 paths and mounted-route coverage covers 292 operations. Frontend typecheck, targeted lint, all 180 unit tests and the isolated production build passed. ## Product binary upload checkpoint (BG-05)

Product uploads add `POST /admin/catalog/products/{productId}/assets/upload` and `POST /admin/catalog/products/{productId}/images/confirm`. Both require the existing catalogue administrator role (ADMIN/SUPER_ADMIN with verified MFA), CSRF and the shared byte-verification lifecycle. Upload limits are 10 MiB, non-animated JPEG/PNG/WebP, 32–8192px per side, at most 40 million pixels and metadata-free WebP output within 2048px. Upload confirmation accepts alt text up to 240 characters; the existing image metadata editor retains its 250-character limit. Preparation never creates a visible gallery row. The confirmation receipt contains the attached image and new gallery version; read the product again for its complete gallery.

The existing `POST /admin/catalog/products/{productId}/images` still accepts hosted HTTPS `url`, `altText`, `sortOrder` and `isPrimary`. Existing PATCH and DELETE routes edit/remove both kinds of image. Uploaded records carry an internal `mediaAssetId`; external records do not. Projections expose `source: UPLOADED | EXTERNAL`, nullable dimensions, and safe display URLs without that internal relation or object keys. Uploaded URLs are immutable through metadata PATCH; upload a new file to replace an uploaded image. Removing an uploaded row queues its owned object for cleanup in the same transaction. Removing or changing an external URL never deletes the external object.

Migration `20260930030000_product_media_version` adds `Product.mediaVersion` with a zero default and nonnegative check; it changes no existing images. Confirmation requires `expectedVersion`; hosted-image create/PATCH/DELETE accept it optionally for compatibility. All image writes take the existing product advisory lock and increment the counter. The frontend sends the current version for both image sources. Compatibility editing remains unchanged. Older clients that omit the counter retain their existing serialized write behavior; they do not receive optimistic conflict protection.

New attachments through either path are limited to 12 total product images. Existing larger galleries remain readable/editable/removable, with new attachment blocked until below the limit. Ordering remains `sortOrder`, then image ID. Selecting `isPrimary:true` replaces the previous selection. Existing semantics are preserved: the first image need not be primary, clearing a primary permits no primary, and deleting the primary selects no automatic replacement.

Public uploaded-image reads use `GET /public/catalog/products/images/{imageId}` and require **both** an active product and active category. Administrator projections use `GET /admin/catalog/products/{productId}/images/{imageId}/content` for authenticated preview, including inactive products/categories. Both return verified WebP with `private, no-store` and `nosniff`; removal revokes subsequent reads. Hosted URLs retain the existing frontend host allowlist and external hosting behavior. No personal customer media is exposed by these routes.

The admin product editor distinguishes “Upload file” from “Use hosted image URL”, uses upload preview/progress/cancel/retry and review, and retains the existing metadata/ordering/primary/removal controls. Uploaded image editing hides the server-owned URL. Failed verification leaves the existing gallery unchanged. The same public product components accept only the new narrowly allowlisted public image route, with a separate explicit administrator-preview opt-in.

## Reproducing the browser harness

Use the existing test database creation/migration scripts on an empty isolated database first. Supply its normal `DB_*` settings and `TEST_DB_NAME`; do not target the application database.

Run `npx tsx tests/helpers/managed-media-api-server.ts` from `backend`. It writes synthetic sessions and an image to the OS temporary directory by default (`allied-bg-browser-sessions.json` and `allied-bg-photo.png`). `BG_DIRECTORY_SESSION_FILE` and `BG_MEDIA_IMAGE_FILE` can select other absolute locations outside the repository. Select `customer-directory.spec.ts`, `profile-photo.spec.ts`, `garage-media.spec.ts` `service-media.spec.ts` and `product-media.spec.ts`. Use a distinct `--output` directory when other browser tasks run in the same workspace. The HTTPS storage hostname is intercepted only by these tests and forwards the selected bytes to a loopback test route; confirmation and owner reads execute the real validation, database and API logic. This does not certify the live S3 signature, CORS or encryption configuration.
