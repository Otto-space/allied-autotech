# Processing jobs contract and local verification

Milestone 93, `/admin/processing-jobs`, passed local acceptance on 19 October 2026. See the [frontend design and verification report](../../frontend/docs/page-quality/work-processing-jobs.md). Deployed and application-wide acceptance remain open.

## Current inspection and retry boundary

New `GET /admin/operations/jobs/:source/:jobId` accepts source outbox/webhook and a UUID, with no query parameters. It returns the safe current row even after it leaves the failure/processing collection. Outbox states include PENDING and PUBLISHED; webhook states include RECEIVED and PROCESSED. Relevant published/processed/failed timestamps supplement the existing safe fields. Missing jobs return404. Payloads, provider identity/hash/signature facts and raw diagnostic errors are excluded. No worker or external provider runs during inspection.

List and current reads recheck the current actor/session under the existing access lock and append minimal READ events in the same transaction. Current reads record resource OPERATIONAL_JOB, physical source and resultCount1; list reads retain OPERATIONAL_JOBS/resultCount. Admin/Super Admin, verified privileged sessions and private/no-store responses remain authoritative. Existing list error keys remain compatible nullable fields but always return null; sensitive diagnostics belong in authorized operational logs.

Retry adds optional `expectedUpdatedAt`, checked in the same conditional update as expectedAttempts and FAILED/DEAD_LETTER status. Existing callers may omit the revision. The UI supplies it. The current actor/session is rechecked inside the mutation transaction. Outbox resets to PENDING, webhook to RECEIVED, while attempts and provider idempotency keys remain unchanged. Notification-delivery retries atomically reset the matching failed/dead-letter undelivered notification; a missing/ineligible delivery rolls back the queue update. Existing CSRF, rate limits, worker consent/provider checks, automatic attempt budgets and STATUS_CHANGE audits remain intact.

The receipt still returns exact id/source/RETRY_REQUESTED/attempts. Queue acceptance is not evidence of delivery, payment settlement or the outcome of a prior unknown request. There is no schema/migration change. OpenAPI export/validation and route coverage pass with306 paths,360 operations and four explicit infrastructure routes; frontend generated declarations are updated.

## Connected frontend verification and rollout

All 22 production browser scenarios, seven frontend units, seven-width/14-state Axe checks, four native concept comparisons, final build/standalone and 14 matching source hashes pass. The frontend preserves drafts during explicit refresh, checks fresh account/current record state, sends the exact revision and validates the receipt. Minimal persistent pending markers prevent automatic replay; unavailable storage blocks submission and revoked access clears private facts.

The connected production browser/API/isolated database workflow queued exactly one outbox event and one webhook, producing exactly two STATUS_CHANGE audits.
