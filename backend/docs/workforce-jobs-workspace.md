# Managed workforce jobs queue

The existing `GET /staff/workforce/jobs` adds optional `q` and `workStatus` filters and returns `generatedAt` plus the same transaction's own `access` snapshot alongside `items` and optional `nextCursor`. No endpoint, permission or database schema is added. Release the compatible backend before the updated frontend.

## Search, filtering and authorization

- `q` is trimmed, at most 120 characters, and rejects control characters. Search matches work-order number, service name, vehicle make/model and registration case-insensitively. Backslash, percent and underscore are escaped as literal characters for Prisma contains filters. Customer identities, administrative notes and financial fields are not search targets.
- `workStatus` accepts the seven existing work-order states plus `NOT_CREATED`. The latter means no work order; it is not a booking state. Search, work status, cursor and the existing authorized booking scope are combined with AND. No client-provided branch or assignee override is supported.
- Existing UUID ascending order, exclusive UUID cursor, default 25/max50 page size and next-cursor behavior remain. There is no total-count claim, time sort or snapshot across separate page requests. Records can change between requests.
- Workshop leads see eligible branch records; technical staff see assigned records within their active branch responsibilities. Existing active-account, verified-email, MFA, enrollment and assignment checks and transaction locks remain. Revoked and nontechnical access is denied. The preexisting job projection is unchanged.
- The bookings queue continues using its original query and response contract. Other queues do not accept these job filters. Private/no-store responses and minimal successful READ audits remain; search text is not added to audit payloads.

The frontend validates URL fields before fetching and excludes its bounded `_trail` cursor history from API calls. It validates unique rows, pagination shape, JOBS_READ, branch/assignee ownership and the returned access snapshot against the shell. Failed, loading or mismatched reads hide retained records. Applied filters and paging survive reload, browser Back and the existing job-detail return link. The list itself sends no business mutations.

Connected production Edge → Express → PostgreSQL verifies technician and workshop-lead paging, query reload, previous/first/browser Back, job-detail return, literal search, combined state filtering, empty/reset/refresh, and revoked-account rejection before a jobs request. Sixteen READ audits correspond to the successful queue/detail reads. Original hashes across 18 domain tables are unchanged and all owned temporary sessions were removed.

Setup retained two synthetic services, one customer vehicle and 30 bookings (29 work orders) for connected verification.
