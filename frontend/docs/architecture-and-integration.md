# Frontend architecture and integration

Staff administration reuses the directory, private account details and shared dashboard shell. Administrators can search by exact email, promote an existing verified customer to branch staff and invite an existing verified staff account to ADMIN. Generic role edits only permit owner-controlled ADMIN-to-STAFF demotion; self/owner targets remain read-only. Promotion, invitation and revocation require current-password proof plus existing MFA/CSRF. Access mutations re-read the selected account and compare user/profile revisions before sending the exact body; this narrows stale edits but does not replace server optimistic concurrency. Successful responses are checked against the requested target and result. Unknown results lock further submissions for the current screen.

Invitation creation reports queued email only and warns that prior unused invitations are replaced. Status/filter/cursor views and reviewed revocation use the safe invitation projection. Acceptance requires the existing intended staff account with MFA and current-password proof. The page strips the fragment/query from history, uses no-referrer metadata, keeps credentials out of browser storage and clears sensitive inputs/session data on account changes. Explicit CSRF-protected confirmation triggers atomic acceptance; it preserves credentials, revokes sessions and requires sign-in again. The backend rechecks recipient binding and inviter authority under access-change locks. Real email delivery remains environment-dependent and was not exercised.

The administrator audit log uses the actual append-only read projection. User role is a current relation, not historical role evidence; absent actor references remain unknown. Before/after JSON may contain selected fields only. Native expandable sections defer pretty-printing until opened and render escaped text in keyboard-scrollable regions. Links to current records are restricted to supported internal routes and UUID references. Filters stay in memory and reset with the dashboard session boundary. Optional date inputs use Lagos time; two-sided ranges enforce the backend's ordered 90-day maximum. Every backend audit read appends a separate privileged read event.

Administrator processing jobs, payment exceptions and disputes share a typed queue shell for role gating, read/error states, filters, cursor navigation where supported and reviewed mutations. Their domain adapters preserve backend retry-attempt and exception-status guards. Unknown outcomes are locked by record/source for the lifetime of the screen, including filter changes. Mutation responses are parsed before acknowledging success. Raw job exception fields are excluded from the runtime UI projection; no event payloads or arbitrary server failure messages are rendered.

Job retries can trigger notifications or payment webhook processing, so they require a reason and explicit consequence review. They do not optimistically confirm delivery or settlement. Jobs intentionally lack cursor controls until the backend implements its advertised cursor; anomalies and disputes use the actual working pagination contract. Dispute amounts are labeled as disputed amounts, and exception closure does not imply a payment/refund/dispute financial outcome.

Customer manual payment reporting accepts only the backend's BANK_TRANSFER/POS/CASH methods and reports existing payments for review; it does not initiate transfers or invent receiving bank details. The current request amount stays server-owned. Field values and opaque upload tickets remain in memory, and account invalidation aborts pending upload work. Eligibility follows pending attempts and server deadlines; temporary refreshes disable the form while preserving its selected file and fields.

`signed-upload.ts` and `file-upload.tsx` now share transport and interaction behavior across customer evidence and vehicle documents. Domain adapters retain distinct token names, MIME/size contracts and preparation endpoints. Customer evidence supports PDF/JPEG/PNG up to 10 MiB. File bytes go only to approved HTTPS storage with signed headers and without application cookies/CSRF. Evidence is attached only by a separately reviewed manual submission. Evidence-bearing unknown outcomes remain locked because the backend revalidates expiring evidence before replay; original key/body recovery is available without evidence.

Staff payment records and administrator refunds use the backend's actual attempt/refund projections with runtime parsing. Request amounts stay decimal strings in integer kobo; captured amounts are never labeled as remaining refundable balances. Manual review and refund decisions require explicit consequence review and retain an unknown-outcome lock across queue filters. Refund creation alone supports idempotent recovery: the original body and random key remain in memory, and changing filters or starting another mutation is disabled until that request is reconciled. No credentials or refund recovery data are persisted in browser storage.

Private payment evidence reuses approved-host, expiring document access and is fetched only on demand. Administrator-only refund reads are not issued for staff. Approval, provider pending/processing, operational attention and successful refunds have separate text; only refreshed server status confirms the recorded result. Browser fixtures do not certify backend financial locking, authorization or provider behavior; identified gaps are tracked in the release blockers.

This describes the current implementation. It does not certify completion of the full brief; use the [coverage ledger](api-coverage.md), [validation record](validation-progress.md) and [release blockers](release-blockers.md) together.

## Application boundaries

- `app/` contains Next.js App Router pages. Public service, part and vehicle detail pages fetch public API projections on the server and pass initial data into interactive components. The root layout renders dynamically to support per-request CSP nonces.
- `app/components/` contains public, account and workshop interfaces. Customer pages live under `/dashboard`; staff and administrators share `/admin` with role-filtered navigation. Backend authorization remains authoritative for every request.
- `lib/api/generated.d.ts` is generated from the sibling backend OpenAPI artifact. `contracts.ts` extracts request-body types. Separate runtime Zod schemas validate the actual response projections because the OpenAPI response definitions are incomplete.
- `lib/api/client.ts` owns browser requests, error normalization, request timeouts, in-memory CSRF state and session generation. `use-resource.ts` owns component-local reads, cancellation, stale responses and explicit refresh/error states. No shared cache stores customer records.
- `lib/forms/` contains reusable validated form values. `lib/format/` converts integer kobo to display amounts and formats dates in Africa/Lagos. Public business details and approved-media rules live in their dedicated library modules.

## Request and session flow

The browser uses same-origin `/api/v1` URLs. Next.js rewrites them to the validated server-only `BACKEND_ORIGIN`. The browser never reads the HttpOnly session cookie or handles a bearer token. Public server-side detail requests use public endpoints without user credentials.

Cookie-authenticated mutations obtain a CSRF token through the existing backend endpoint. Concurrent CSRF reads share one in-flight request. Session changes invalidate that token and advance a generation counter, so responses from an earlier account cannot populate the current account's request state. A cross-tab channel broadcasts invalidation only; it does not contain account records or credentials.

`DashboardShell` verifies the session, role and MFA requirement before mounting account content. It removes private content on session invalidation and rechecks on returning to a visible tab. Those UI guards supplement the backend's ownership, role and branch checks; they are not a substitute for them.

## Consequential changes

The API client does not automatically replay mutations. Endpoints that provide an idempotency contract receive a dedicated key; uncertain customer checkout/booking retries preserve their original payload and key. Payment return navigation is not evidence of successful payment: the payment screen reads and verifies backend state, and pending states prevent initiating another charge.

Workshop changes use the endpoint's expected version or quotation revision and a review dialog. Catalogue-part prices are omitted from quote/work-order requests so the server prices those parts. Labour, fee and tax entries convert decimal NGN strings to integer kobo using `BigInt`. Draft replacement follows the backend's creation of a new draft and voiding of the old draft.

For quotation, line-item and slot creation without idempotency support, an uncertain response disables the submitted form and prompts review of refreshed records. No automatic retry is issued. This protection does not eliminate the need to inspect backend state after an uncertain network outcome.

Inventory movements, reservations and releases preserve one payload/key per reviewed operation. An unknown outcome pauses new stock mutations and offers an explicit retry of that same request; refreshed server balances remain authoritative. Cancelled or rejected reviews preserve draft input. Confirmed changes reset forms and refresh balances, history and reservations. Reorder updates use the current inventory version. A stock sale does not create an order, invoice or payment. Reservation expiry validation can reject a late retry before idempotency replay; this backend recovery limitation is tracked in the release blockers.

Staff invoices select an existing authorized source and send only its type/ID and an optional due date. The backend supplies invoice amounts and eligible deposit credit. Draft creation is not retried automatically; an unknown result locks the original form while staff review refreshed invoices. Issue/void actions use expectedVersion and explicit review. Issuing is separate from payment confirmation, and voiding does not cancel an order or refund a payment.

Vehicle stock records and sale listings have separate identifiers and versions. Staff stock creation uses the current profile's assigned branch; administrators select a branch. Stock specifications and internal acquisition cost/date are separate from the public asking price. Listing content, price and publication each have a reviewed mutation. Prices are immutable in reserved/sold/archived states; content editing is unavailable for sold/archived listings. Reserved/sold purchase transitions are not offered as generic publication actions. Stock/listing edit drafts survive a newer background response and require explicit field reload before saving, so a newer version cannot silently overwrite the user's draft or be applied to stale fields. The backend staff query accepts some filters it does not implement; the UI exposes only the applied subset recorded in release blockers.

Vehicle photos and private documents share the checked upload transport but have separate attachment mutations and privacy explanations. The parent record is refreshed after review; attachment forms reset only when the returned attachment IDs change. Unknown creation outcomes lock the original form. Public image previews use the backend image route only for available listings at an active branch. Private document access is requested explicitly and never loaded as a public image. Document sizes arrive as decimal strings from Prisma BigInt serialization. Document assessments use the document version, preserve concurrent drafts and require explicit reload. The staff projection exposes only the latest condition report; its summary/findings are also public. Missing report-history/download and attachment edit/delete contracts are recorded in release blockers.

Staff inspection management uses the actual paged list projection; no individual-read route is invented. Status changes preserve their original version until explicitly reloaded. Confirm/reschedule requests include complete Lagos start/end times; cancellation requires a reason. Staff changes are assigned by the backend to the acting profile, while administrators can select an active branch assignee. Inspection progress does not create a purchase reservation, payment or condition report. Report creation lives on the stock record, with a paged optional lookup of completed inspections whose listing IDs belong to that stock. Reports preserve text/number/boolean/null findings, reject duplicate names to avoid silent replacement and require explicit public-content review. Unknown creations stay locked because the latest-report projection cannot prove whether an older report was saved. Customer/public report parsers accept nullable odometers from the actual backend contract.

Staff vehicle purchases use a separate projection for customer references, branch and handover versions. Negotiation submits integer kobo and the purchase version; reservation, full payment and delivery are distinct states. Handover creation requires a paid purchase and an operator staff profile. Status changes use the handover version, not the purchase version. Completion is confirmed only after a fresh server read. An uncertain creation is not automatically resent. Cancelling a handover currently leaves the purchase pending with no API-supported replacement; the UI explains this and the recovery rule remains a backend release dependency.

Optional signed PDFs use a separate upload ticket, SHA-256 checksum and signed PUT before reviewed handover attachment. Storage URLs must use an approved HTTPS host outside the application origin; uploads omit credentials and reject unexpected headers. Account invalidation aborts pending transfers and removes selected files, tokens and download links. Private access is requested explicitly, checked against the host allowlist and retained only until its server-backed expiry. `ASSET_STORAGE_HOSTS` contains only public runtime hostnames and is empty by default. Real storage CORS, byte verification and downloaded-content checks remain required; the backend synthetic fallback is documented as a release dependency.

## Rendering and security headers

`proxy.ts` supplies a per-request CSP nonce and private/no-store headers for account and payment routes. Script and production style elements require the nonce. Inline style attributes remain allowed for Next/Image layout. Approved image hosts are validated before entering the CSP; arbitrary API-provided image URLs are not accepted.

`SITE_INDEXING` defaults to disabled. This is a search-index directive, not access control. Production domain-dependent SEO work and deployment-level HTTPS/cookie checks remain unfinished.

## Product compatibility and images

The administrator parts list opens a selected-record editor using its captured list URL; the backend has no individual administrator product GET. Typed projections validate nullable fitment fields and image metadata. Before a write, the editor rereads that page and compares its product/child projection, since child mutations do not update the parent timestamp. This is a frontend stale-draft guard, not atomic concurrency control. All compatibility edits send both year bounds; image primary replacement and deletion consequences are reviewed explicitly. The shared catalogue editor also rechecks edited fields and expected service versions before saving. Uncertain writes are not automatically replayed; locks survive local editor reselection and are cleared with account-scoped state.

Product images use existing durable public URLs; this API has no product upload facility. Draft URLs are never fetched. Saved previews use the existing public media allowlist and neutral fallback. Unapproved HTTPS URL records can be stored under the backend contract, but their images stay unavailable until the host is configured. Private document upload/access remains a separate contract.

## Promotions and discount previews

Promotions have dedicated administrator routes and typed runtime projections. Percentage inputs convert exactly to integer basis points; money inputs convert to integer kobo strings without floating-point multiplication. Creation starts disabled until the operator enables it. All editable settings are reviewed, including nullable limits and code, with the inactive discount representation explicitly cleared. Updates use the backend row-lock/expectedVersion contract. Refresh preserves a stale draft until explicit reload. Missing/malformed or contradictory write responses cannot be acknowledged as successful or automatically replayed.

Lagos date controls support seconds and milliseconds, preserve untouched stored timestamps, and require an ordered window. Enabled is a configuration flag, not a guarantee of current eligibility. Records without a code are not automatically redeemed; zero fixed discounts/caps cannot produce an eligible discount. Usage counts and remaining redemptions have no read endpoint and are not inferred.

The customer code-preview POST uses the current server-provided cart subtotal and returns an advisory server discount. The preview response must match the submitted code and contain a positive discount no greater than the subtotal. Changing the code/cart, refreshing the cart, starting checkout or invalidating the session discards the preview and aborts pending reads. Only code/branch/fulfilment are passed to checkout; the server recalculates and atomically consumes eligibility there. The backend orders documentation broadly says client subtotals are never accepted; this is true of checkout, while the actual preview schema intentionally accepts an advisory subtotal. Preview never reserves or commits a redemption.

## Account security management

Customer and staff security pages share password, session and factor panels with independent runtime-validated reads. A confirmed password change invalidates all in-memory private state before accepting the rotated CSRF token; the current tab explicitly revalidates its session. Broadcast messages carry only a random tab source and an invalidation type, so a tab ignores its own broadcast while other tabs clear account state. Wrong password reauthentication is distinguished from an expired session only at the two applicable endpoints.

Passwords never appear in review facts and are cleared after attempts or cancellation. A rejected credential proposal cannot be resubmitted without returning to the form. Unknown password/session/factor mutations remain locked. Factor removal explains that existing sessions and recovery codes survive. Pending factors have no removal control; privileged accounts cannot remove their final active factor in the UI, and the backend now serializes the final-factor decision with removal; isolated database regressions cover concurrent attempts.

Recovery replacement explicitly invalidates every previous code. Responses require a unique, nonempty array; codes stay in component memory with no automatic clipboard, download, URL or browser-storage persistence. Dismissal and account invalidation remove the display. A lost response cannot be recovered by GET; another replacement requires a fresh consequence review and invalidates any previous set. Enrollment and sign-in challenge behavior is described in the MFA section below.

## MFA enrollment and verification

The MFA route validates the current session before offering a workflow. An already verified session can follow `/mfa?setup=1` from either account security page. An MFA-pending session selects an existing authenticator, recovery code or security key. First-factor setup is offered only after all three method checks return the backend's explicit unavailable code; failed or malformed reads do not grant setup. This client restriction is not a backend authorization boundary. The backend now enforces this restriction under account/session locks, including a recheck at activation.

All six MFA POST operations have typed runtime projections. TOTP setup requires a valid factor reference, base32 secret and matching otpauth URI; the UI displays the manual setup key without linking to or fetching that URI. Factor activation validates both a rotated CSRF token and unique nonempty recovery codes. Single-use codes are cleared after every attempt. Unknown verification outcomes are locked, with a read-only session check and sign-in recovery path rather than replay. Server TOKEN_INVALID errors receive MFA-specific wording instead of password-link instructions.

WebAuthn preparation and the browser ceremony are separate explicit gestures. Registration explains replacement of existing recovery codes; optional names are trimmed and sent only with credential verification. Browser responses are sent to the supported endpoint, and only the server response confirms activation/authentication. Cancellation and navigation abort pending browser ceremonies. Runtime parsers preserve the backend's required user-verification policy. The installed SimpleWebAuthn 14 API and cancellation behavior were checked against [official browser documentation](https://simplewebauthn.dev/docs/packages/browser).

Successful rotation broadcasts account invalidation to other tabs while the current MFA view retains only its confirmed recovery-code result. Dismissal, navigation or an external account event removes those codes; no URL/storage/clipboard/download persistence is introduced. Continuation rereads the session and routes customers to customer security and privileged roles to staff security. API responses decoded after caller cancellation are discarded. Authentication pages use an inline help link so floating support controls do not cover security inputs or recovery actions.

## Backend MFA correction and integration boundary

The four enrollment routes retain their success contracts but now reject an unverified session with existing factors/recovery codes using MFA_REQUIRED. Controllers pass the middleware-authenticated session reference and CSRF digest internally, never accepting them from a body. The service locks User before Session, checks current ownership/status/deadlines/revision and serializes the bootstrap decision. Cryptographic verification occurs outside the locked transaction, then activation repeats the checks. Factor/code/audit/session changes commit together. Role/status changes serialize on the account row; NO KEY UPDATE avoids unnecessarily blocking child foreign-key checks.

Factor removal rechecks the password digest and current role under the account lock, then commits its minimum-factor check, removal and audit together. Recovery replacement shares this lock. The existing policy that factor removal preserves sessions/recovery codes is unchanged. Password-change atomicity and failed rotation after a single-use sign-in challenge remain separate open issues; this correction does not claim to resolve every identity race.

When an older customer session is still marked MFA-optional but the backend requires existing-factor verification for enrollment, the UI exposes an explicit verification action and switches to the challenge flow. It does not reinterpret the session response or retry enrollment automatically.

## Notification inboxes and optional delivery

Customer `/dashboard/notifications` and staff `/admin/notifications` share a validated inbox and preference editor, using only their respective `/customers/notifications` and `/staff/notifications` endpoints. Staff reads remain own-account reads, not a recipient directory. Independent resource requests avoid serial loading; cursor/type/category/unread changes cancel stale requests and reset page history. Session invalidation clears private reads and unmounts pending reviews.

Read-all review explicitly includes records outside visible filters/pages. Individual responses must match the selected ID and include a read timestamp; all-read responses must contain a nonnegative integer count. Preferences are sparse: absent operational entries mean enabled, while marketing requires enabled plus a recorded consent timestamp. Security/transactional delivery categories have no editable controls. Enabling marketing opens explicit consent review; no message or provider call is sent by the frontend. Provider availability and contact details still govern actual delivery. Preference changes do not recall queued deliveries. There is no preference revision field: an explicit later write can replace another tab's value. Unknown or contradictory mutation responses are not replayed and pause further writes in the affected view. Reloading and reviewing current values is a new user decision, not proof of the earlier request's outcome.

## Review publication boundary

Customer reviews support BUSINESS, PRODUCT, SERVICE, ORDER and VEHICLE_TRANSACTION. Completed record pickers reuse parsed customer order/booking/purchase projections with cursor pages; customers never have to supply internal identifiers. Before creation, a detail read must still contain the selected completed source and exact relationship fields. This improves recovery while server ownership, eligibility and uniqueness remain authoritative. A failed preflight sends no creation request. Creation has no idempotency contract, so unknown results lock the form and direct the customer to submission history.

The administrator queue is unavailable to ordinary staff. Moderation sends the exact expectedVersion and explains public approval, customer-visible notes and notifications. Rejection requires a reason. Saved responses must match the selected review, decision, incremented version and supplied note. Unknown outcomes lock the affected review across filter changes. No edit, deletion or reversal endpoint is invented. Public rendering parses only the public projection; customer identity, internal references, status and moderation notes are stripped even if extra fields appear in a response. Public feedback is currently browser-loaded, with server-rendered SEO work explicitly outstanding.

## Customer care

Public contact submissions and authenticated customer creation share validated forms while sending distinct backend bodies. Related products, services, listings, bookings, quotes, orders and vehicle purchases are selected from existing API projections; raw identifiers are not user inputs. Branches are explicit unless inherited from the related record. Staff contact information is parsed only for staff screens; anonymous submissions are clearly distinguished from account-linked conversations. A public acknowledgement confirms receipt only, without promising an appointment, refund, response deadline or account visibility.

Dedicated `/dashboard/support/[kind]/[supportId]` and `/admin/support/[kind]/[supportId]` routes key private state by conversation. Detail parsing validates the requested identifier and discards embedded message arrays. The message endpoint supplies oldest-first cursor pages; this UI uses manual refresh plus existing online/visibility refresh, not live polling. Customers cannot render INTERNAL items even if a malformed response contains them. Failed list/detail/message reads hide cached private content; failed detail reads also unmount the reply draft. Account invalidation unmounts all private state. Conversation subjects/contact values wrap at narrow widths; floating quick-help controls are omitted from customer-care pages so they cannot cover the conversation.

Replies re-read thread identity and closed status before sending. RESOLVED can still receive messages; CLOSED cannot. Customer replies send message only. Staff selects CUSTOMER or INTERNAL and reviews visibility before submission. Assignment/status/priority updates use expectedVersion; resolving requires customer-visible text. A staff action with an unknown outcome locks further changes in that view. Creation locks persist across category switches and reply locks preserve the draft after an uncertain result. These are in-memory safeguards, not server idempotency or a substitute for inspecting persisted state after a reload. No unsupported reopen, anonymous-thread linking or attachment endpoint is invented.

## Cart maintenance and expiry policy audit

Cart clearing uses the actual DELETE `/customers/cart` empty-body contract. The review displays parsed quantities and exact integer-kobo totals. A fresh parsed cart must match the reviewed snapshot before deletion; failure or changed contents sends no DELETE and requests a new read. The success envelope has no data payload, so acknowledgement is followed by a cart refresh. This preflight is not an atomic compare-and-delete: the backend accepts no expected cart revision. Unknown clear/item mutations pause further edits and checkout in the current view, including after refresh. Original idempotent checkout replay remains separate. Account unmount aborts active cart/checkout requests, and failed cart reads remove cached contents from rendering.

Administrator bulk order and vehicle-reservation expiry routes are intentionally not called by the browser. Source inspection found manual paths lacking the corresponding system paths' payment-in-flight/review exclusions; the vehicle manual path also does not recheck its deadline under the transition lock. Each candidate is independently committed. The overview explains unavailability and links to record review without presenting a nonfunctional button. Backend policy alignment and isolated settlement/concurrency verification remain required; no operator override policy is invented.

## Vehicle payment requests

Purchase detail now owns a separate payment-history/request component keyed by transaction ID, not revision. The parent validates the returned purchase ID and hides a failed detail read. The child stays mounted across parent read failures so an uncertain payment reference is retained without rendering private purchase content. Customer payment history is read through every cursor page and filtered by vehicleTransactionId before storage/rendering. Repeated cursors, duplicate IDs, malformed pages and the 100-page safety bound produce an error, never a false empty history. There is no fabricated server target filter.

All four server-supported purposes are available. Reservation/partial requests require a positive team-set amount; full payment is unavailable after a confirmed payment. Paid/terminal purchases, passed or malformed reservation deadlines and unresolved payment requests/attempts prevent fresh creation. No customer-entered amount or calculated remaining balance is sent. A new request is reviewed and then preflights the purchase revision/prices/deadline/status and complete payment history; the backend remains amount/ownership authoritative. Confirmed responses must match the vehicle source and purpose before the UI links to the existing payment-method screen.

Unknown creation retains one original idempotency key/body while disabling new purpose selection. Explicit recovery reuses that request even if current eligibility changed; a rejected recovery does not unlock fresh creation. This does not repair the backend's mutable-source-before-replay ordering or races between distinct keys. Account changes cancel requests and discard private state. Payment-request creation does not charge a method, accept reservation terms or extend a hold. Payment detail now validates its requested identifier and links back to the vehicle purchase.

## Public search metadata and discovery

`lib/seo.ts` centralizes configured canonical identity, public page metadata, private route classification and supplied business structured data. `SITE_ORIGIN` must be an approved HTTPS origin without path, credentials, query or port. It is never inferred from request headers. `SITE_INDEXING=enabled` has effect only with a valid origin; leave indexing disabled in development/staging. This is indexing policy, not access control.

Public pages have distinct titles/descriptions and Open Graph/Twitter summaries; images/social-profile claims are omitted until approved. Query variants retain their base canonical but are noindex. Public details deduplicate metadata/content reads within a render, validate UUID and response identity, preserve Next not-found interrupts, and omit browser credentials. Homepage AutoRepair JSON-LD contains only supplied name/address/phone/email and the configured origin, escapes HTML script terminators, and uses the CSP nonce.

`/robots.txt` is dynamic. `/sitemap.xml` queries only the three existing public list endpoints, concurrently across domains and sequentially within each cursor chain. It requests 50 IDs per page, rejects repeated IDs/cursors, caps each scan at 100 pages and all scans at 15 seconds, with existing six-second fetch timeouts. Any incomplete scan returns HTTP 503 with Retry-After and no-store, not a partial successful sitemap. Missing indexing configuration returns 404 without fetching. No invented modification dates, rankings or private/account URLs are emitted. The endpoint has no cross-request catalogue cache, preserving unpublication behavior; very large catalogues require a coordinated partitioned sitemap design. Concurrent edits can invalidate a scan because the API offers no snapshot token.

Implementation references: the installed Next.js metadata/robots/sitemap/notFound guides and [official metadata API](https://nextjs.org/docs/app/api-reference/functions/generate-metadata), with [Schema.org AutoRepair](https://schema.org/AutoRepair) for supplied business facts. Search-engine acceptance and field performance are not established by local verification.

## Public discovery first render

`loadPublicSeed` validates public data before passing it into client list components; its React cache is scoped to one server render and never forwards user credentials. The four collection pages use the same path/parser for metadata and page content, avoiding duplicate backend calls. Failed collection reads produce an inline safe error and noindex metadata, rather than a fabricated empty result. Homepage preview reads run concurrently; each failure is independent. The homepage awaits those results before rendering its content so the preview headings remain visible even when JavaScript is disabled. This can delay the first response up to the existing six-second fetch timeout and remains part of performance acceptance.

The existing resource hook accepts an optional validated initial result/error and opt-out from its initial fetch. Other callers preserve default behavior. Subsequent filter/cursor changes, explicit refresh, reconnect and tab visibility perform normal reads; the server seed is not restored after those reads. Resource session invalidation discards its scoped state; only `/public/` reads automatically reload, while private views retain their authorization reassessment boundary. The public header listens to the existing account-invalidation BroadcastChannel and delegates to the same generation/CSRF invalidation function used by authenticated shells; messages contain no account data. This resource behavior does not itself clear independent mutation-result state owned by other components. Catalogue/review consumers hide cached cards after a failed refresh rather than displaying withdrawn material as current.

No-JavaScript access covers public content and ordinary links, including first-page item details. A visible noscript notice explains that filtering, further pagination and refresh require JavaScript. Those controls keep their existing API-based behavior and do not yet encode filters into shareable navigation URLs. Public schemas strip unknown fields before both HTML and hydration serialization; approved reviews do not expose customer names or moderation fields. No aggregate rating is inferred from a single review page.

## Public detail account mutations

ServiceDetail, ProductActions and VehicleActions use useAccountMutation for account-scoped operation lifetime. The public header receives the existing cross-tab invalidation signal; the hook aborts its pending browser request and synchronously resets local results, errors, booking consent/slot/branch/idempotency attempt, cart quantity and inspection date/notes. A request from the old session cannot write a success/error back into the current form. Completion of an older request cannot unlock a newer request. Unmount also aborts pending work. This does not cancel a server operation or establish backend ownership: the notice directs the customer to inspect their account before another submission, and no request is automatically replayed.

Booking retries after an unknown response retain the original body and key within the same session. A session change discards that attempt; any later user-initiated booking requires selecting a slot and accepting terms again and receives a fresh key. Authentication failure uses the same existing invalidation path and leaves an account-recovery link. Anonymous contact/support forms and private dashboard workflows have separate state lifetimes; this hook is not a claim that every application form has been audited.
