Route: `/dashboard/bookings/[bookingId]`. Expanded milestone 32 passed local acceptance on 8 October 2026. This report covers this route and its customer workflows; deployment/provider acceptance and the remaining application routes are separate.

## Audit and implementation

Four baseline widths (390/768/1280/1440) were captured before edits. Three fresh built-in ImageGen concepts, full prompts, token inventory, API inventory and deliberate corrections are saved in [the concept specification](customer-booking-detail-oct-concepts/README.md).

The implementation now separates appointment/vehicle/notes, deposit, recorded milestones, appointment changes and quotation documents. It preserves the actual shell, logo and support controls. The route owns one semantic breadcrumb using the service name. Quicksand, ink/off-white/white contrast, visible controls, responsive quotation rows and the shared review dialog follow the concept specification.

Reviews show exact dates, vehicle, quotation revision/total/expiry and cancellation reasons. The detail parser rejects a different booking identity. Failed manual reads hide prior data; failed background reads retain facts with mutations disabled. Quotation expiry is checked at display time and again against a fresh API response before submission. Schedule/disruption retries retain the original body/key; non-idempotent uncertain changes require a fresh read. Session changes abort and discard pending browser work. Backend ownership, CSRF, transition and concurrency checks remain authoritative.

## Additional real transaction evidence

The isolated Express/PostgreSQL browser harness completed with exit code 0 and no page errors. It forwarded browser requests to the actual API without mocking responses. Quotation rejection and acceptance persisted; acceptance stored the exact 10750-kobo total on the booking. Rescheduling persisted REQUESTED, incremented the customer allowance once and replayed with the same key without a second increment. Cancellation persisted the reviewed reason. Disruption transfer persisted REQUESTED/TRANSFERRED without consuming the customer allowance. A seeded historical verified deposit produced one REQUESTED refund, even on a same-key replay, with no refund ledger entry or completed payout. This verifies refund-request semantics, not a live provider payout.

Foreign booking read returned 404, missing-CSRF cancellation returned 403, administrator access to the customer route returned 403 and anonymous access returned 401. Private staff notes were excluded. Fixture construction initially hit the database's issued-line immutability and verified-settlement requirements; the harness was corrected to create draft lines before issue and supply a valid synthetic verified-settlement record. No production constraint was relaxed.
