# Customer order aftercare

Date: 12 October 2026. Route: `/dashboard/orders/[orderId]/aftercare`.

Status: locally accepted. This is the forty-seventh expanded frontend milestone; the application-wide goal and deployed acceptance remain open.

## Audit and design

The baseline placed a large order section above a full-width stacked form and distant history. Both the submission button and history required excessive scrolling. The breadcrumb did not identify the order. Intake did not recheck the session or fresh order/history before sending; its uncertainty lock disappeared on reload. Copy incorrectly limited duplicate preservation to “active” requests, while the backend preserves every same-kind request that has not been rejected, including approved requests.

Two fresh [desktop and mobile/state concepts](customer-aftercare-oct-concepts/README.md) preceded implementation. The scoped design uses an ink order band, paired form/history panels, compact product rows, readable order breadcrumbs and customer-safe decision details. Mobile stacks context, form and history. Existing Quicksand typography, logo, role navigation, focus styles and the native confirmation dialog remain authoritative.

## Authoritative contracts

Paths below omit `/api/v1`.

| Operation                      | Existing contract and invariant                                                                                                                                             |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Order                          | `GET /customers/orders/:id`; customer ownership, actual order lines, quantities and server amounts.                                                                         |
| History                        | `GET /customers/orders/:id/aftercare`; owned, customer-safe latest 100 requests, newest first. No cursor or all-time total is supplied.                                     |
| Whole return                   | `POST /customers/orders/:id/returns`, `{ reason }`; server includes all ordered products and quantities.                                                                    |
| Selected return / cancellation | `POST /customers/orders/:id/aftercare`, `{ kind, reason, items }`; quantity must be a positive integer no greater than the ordered amount, with unique owned line IDs.      |
| Duplicate                      | Order-row locking serializes intake. A same-kind request whose status is not `REJECTED` is returned unchanged. This is not original-request replay after a later rejection. |
| Decision                       | Review approval does not itself cancel the order, change stock or confirm refund payment. A reviewed fee is not a refund amount.                                            |

Sources: [service](../../../backend/src/modules/orders/order-aftercare.service.ts), [backend schemas](../../../backend/src/modules/orders/order-aftercare.schemas.ts), [routes](../../../backend/src/modules/orders/order-aftercare.routes.ts), and [frontend parsers](../../lib/api/aftercare-schemas.ts). Customer projections exclude internal inspection notes, policy snapshots and staff review reasons. No frontend return deadline or eligibility cutoff is invented.

## Implementation

[CustomerOrderAftercare](../../app/components/customer-order-aftercare.tsx) validates the route and customer session, keys private state by account/order, reads the order and history independently and verifies record/line identities. The [route stylesheet](../../app/dashboard/orders/[orderId]/aftercare/aftercare.css) scopes the design to this page. The dashboard shell suppresses its generic breadcrumb only for this customer route; staff review and fulfillment evidence retain the existing screen.

[AftercareIntake](../../app/components/aftercare-intake.tsx) preserves the existing endpoints and confirmation facts. It retains request kind, scope, products, quantities and explanation across reload, rechecks the current customer plus fresh order/history before writing, and rejects a changed reviewed order. The preflight is not an atomic version contract; backend validation and order locking remain authoritative. A returned original request is a valid duplicate result even if its products or explanation differ from the new submission.

[useAftercareWrite](../../lib/orders/use-aftercare-write.ts) saves only an account/order-scoped pending marker before sending. Unknown outcomes survive reload and never replay automatically. Another send requires explicit manual refresh of both order and history, followed by acknowledgement. Failed or mismatched manual reads cannot be satisfied by a later background refresh. Storage failure blocks submission, rate limits honor `Retry-After`, and unmount aborts the browser operation without claiming to undo a server write. Forms remain editable during reconciliation so drafts can restore, while submission stays disabled.

HTTP success alone no longer clears this form's draft. The returned order request must validate first; only validated success clears the draft. Closing a confirmation without sending preserves both fields and focus.

## Fidelity ledger

Native desktop and mobile renders were compared with the retained concepts. The real shell, fonts, accessible control sizes and authoritative API fields take precedence over generated examples. No new photography is needed for this transactional screen.

| Point                  | Concept / baseline finding                                                        | Correction / verification                                                                                                                                                 |
| ---------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Layout                 | Form/history belong beside each other on desktop, stacked on mobile.              | Scoped 1.15:1 columns, 24px gap, one column below 1100px.                                                                                                                 |
| Form density           | Shared styles reintroduced nested padding and tall rows.                          | Stronger page-scoped selectors remove the extra frame; compact product/quantity rows retain 44px controls.                                                                |
| Copy and quantities    | Long selector values clipped; active-only duplicate copy was inaccurate.          | Short selectors plus explicit all-quantity hint; full non-rejected duplicate explanation retained.                                                                        |
| Typography and palette | Generated branding, green status and collection date are not authoritative.       | Real logo/Quicksand and neutral status; actual server fulfillment method without invented scheduled date.                                                                 |
| Above-fold hierarchy   | Baseline context and form pushed the action and history too far down.             | Compact context band and selected-product rows put the primary action within the 1505?1045 desktop viewport; copy introduces no unverified eligibility or refund promise. |
| Recovery               | Reload could previously unlock another uncertain submission.                      | Persistent marker, both-read manual reconciliation, disabled acknowledgement until valid refresh, preserved draft.                                                        |
| Mobile and dock        | Order summary wasted a row; desktop dock approached the history's rightmost text. | Pair order/status on mobile and reserve more right padding in desktop history. Final desktop/mobile captures and mobile action clearance passed.                          |

## Remaining boundaries

No backend production code, schema or migration was changed for this page. Latest-100 history and non-rejected duplicate suppression are existing bounded contracts. Durable original-request replay would be a separate optional backend enhancement; the current page provides conservative manual reconciliation. Real refund settlement, deployed integrations and the remaining role dashboards keep their own gates. Next route after acceptance: work-dashboard overview `/admin`.

## Original-request recovery contract update

The customer intake now persists its normalized original request and 24-hour recovery key before sending. Reload presents an explicit original-request confirmation; recovery returns the current owned request even after rejection or outside the latest 100 history records. Current draft edits do not substitute for the original payload. Current session/ownership checks, legacy manual reconciliation, staff review boundaries and account-scoped draft behavior remain enforced. See [aftercare request recovery](../../../backend/docs/aftercare-request-recovery.md) for the coordinated API/frontend contract, isolated database evidence and browser verification. This supersedes the original page gate's marker-only recovery limitation; deployed acceptance remains separate.
