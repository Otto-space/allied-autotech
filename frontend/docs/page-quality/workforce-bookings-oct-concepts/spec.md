# Managed workforce bookings — milestone 106 specification

Route `/admin/workforce/bookings`, audited 19 October 2026 after milestone 105 acceptance. This is the single active page. Existing generic queue cards expose service, customer name/phone, schedule and raw status, with no filters, only forward in-memory paging, no explicit empty state and retained data after background failures. Native baselines at430/768/1280/1440 were captured and inspected: no overflow/page errors, but oversized sparse cards and poor information density. Baseline artifacts are outside the repository under `workforce-bookings-baseline-*`.

## Authoritative contract and scope

Existing GET `/staff/workforce/bookings` accepts bounded limit/cursor and returns id, version, service name, customer first/last name/phone, scheduledAt and booking status. Managed active Operations and Customer Service branch assignments supply BOOKINGS_READ; other roles do not gain access by this redesign. Actor/MFA/workforce checks, branch scope, UUID ascending pagination and atomic BOOKING READ audits remain. No booking mutations or compatible managed booking-detail endpoint are available. Do not link to legacy admin details or technical jobs for these roles.

Add optional bounded literal search (trimmed q up to120 characters without controls) and the eight actual booking status filters. All search terms must match service, customer first/last name/phone or vehicle make/model/registration within the authorized scope. Extend the existing response with access/generatedAt and each row's branchId, minimal branch name and vehicle make/model/year/registration. Existing fields remain; never add prices, payment/deposit amounts, staff notes, diagnosis or other unrelated private data. No new endpoint, schema/migration or permission expansion is required. Preserve all technical job and other queue contracts.

## Behavior and acceptance

Search/status combine and apply explicitly across all permitted records. URL holds normalized filters and cursor trail; reload, Back, First/Previous/Next preserve them. Reuse the proven pagination utility, not a new paging protocol. Invalid, duplicated, unsupported/control-bearing parameters prevent requests and offer Clear filters. Harmless refresh preserves an unsent search draft; clear resets it even when the URL is already unfiltered. Hide rows/counts on loading, background failure, scope mismatch, denial or expired responsibility. Empty scope and unmatched filters have distinct messages. Every response must validate identity, references, scope, uniqueness and cursor metadata.

Before acceptance: helpers/URL/scope units; browser tests for both eligible roles, denied roles, search/status/paging/reload/Back, reset, invalid URLs, errors/recovery, malformed/mismatched/foreign data, temporary expiry and long content; seven widths360/390/430/768/1024/1280/1440 plus320 long data, Axe/focus, native430/768/1280/1440 comparisons; targeted shared-shell/queue regressions; type/lint/format/OpenAPI/build and source hashes. Retain old fixtures; do not replay completed mutations. Prior unchanged migration evidence may be reused. Deployed and whole-application acceptance remain separate.
