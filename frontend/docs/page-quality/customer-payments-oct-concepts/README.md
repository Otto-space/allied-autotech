# Customer payments list concepts

Prepared 8 October 2026 before production changes to `/dashboard/payments`, after auditing the customer payment routes, strict queries, owner projection and four baseline viewports. Built-in ImageGen produced the [desktop](desktop.webp), [revised mobile](mobile.webp) and [result-state](states.webp) concepts. Original PNGs remain in Codex storage; these WebP copies change encoding only. The first mobile candidate was rejected because it over-emphasized every row action with filled buttons and changed the guidance surface.

## Written design specification

- Preserve the approved dashboard shell, logo, permitted navigation and utilities. Use a single semantic Overview / Payments breadcrumb.
- Quicksand throughout the operational page: heading 30px desktop / 27px mobile; guidance/state headings 18px; reference 15px bold; body 13px; metadata 11–12px; labels 13px; selects 14px desktop / 16px mobile to avoid mobile focus zoom.
- Ink `#01121A`, red `#E60301`, white and cool canvas `#f4f6f8`; muted text `#435563`, borders `#cbd5df`, control borders `#82939f`. Radius 6px controls / 8px panels. All visible actions at least 44px; selects 48px. Red focus outlines and restrained hover styles.
- Heading **Your payments**, unchanged subtitle **Check a payment here before making another attempt.** Red **Refresh** action with RefreshCw icon; outlined **View invoices** link. No payment mutation on this list.
- Ink guidance strip with CreditCard icon: **Check before paying again** and **A payment attempt is not a confirmed payment. Open the details to check the latest status.**
- White filter panel with **Payment status**, **All statuses**, six supported states, **Rows per page** 10/20/50, **Reset filters**. URL persistence for validated filters, cursor and bounded UI-only previous-page history; never send that history or unknown fields to the API.
- Five-column table: **Payment**, **For**, **Status**, **Amount**, an accessible details-action header. Show reference and real creation date, purpose and supported linked-record links, a neutral readable status with short explanatory copy, the server amount and one **View payment** action. Only `SUCCEEDED` permits **Confirmed amount**; other records say **Requested amount**. Do not derive success from an attempt or redirect callback. Dates and related IDs come from the current owner projection; never display raw UUIDs as names or fabricate linked record numbers.
- Below 1100px use labeled records within one continuous table. Reference and purpose span the record; status/amount share a row; the payment-detail action spans the bottom. Related links remain understated ink text with a 44px target. No large red row buttons or separate floating cards.
- Neutral state labels: Awaiting payment, Processing, Needs review, Confirmed, Cancelled, Expired. Purpose labels cover the seven actual purposes and existing legacy aliases, with a generic Payment request fallback for unknown future values.
- Exact count **on this page** only. Previous / Page N / Next for known traversal; Later page / First page for a direct cursor. Footer **Dates shown in Lagos time.** and **Need help with a payment? Contact support**.
- Loading uses row-shaped skeletons. Failed manual reads hide prior data and offer Retry payments. Transient background failure retains readable data with an explicit stale notice and retry. Initial, filtered and later-page emptiness have distinct recovery actions. Initial empty copy stays **Your payment requests will appear here when created.**, with **Back to overview**. Session changes discard private records and late responses.

## Artwork corrections and constraints

Use the real shell and official logo instead of generated header variants, device status bars, invented trademarks, slogans or a marketing footer. Preserve the primary desktop hierarchy across responsive layouts. Keep filters stacked on narrow screens so their labels and values remain readable; the revised board's single-row arrangement is not feasible at 320px with required targets. Use actual local font files, supported record links, timestamps and NGN amounts. Exclude the states board's USD example and overflow menus, and keep its result-heading position below the filters as in the primary page. No new balances, provider actions, receipts or global financial totals are inferred from the list. No generated image becomes application UI.

## Prompt record

The desktop request specified a complete landscape 1440×1000 composition with the existing 256px sidebar/70px toolbar, exact copy above, four payment rows and footer. The revised mobile request specified two readable 390px panels, one continuous responsive table, ink guidance, neutral underlined related links, and red reserved for Refresh. The state request specified loading, initial empty, filtered empty, failed read and retained background data, using the same palette, controls and payment table anatomy. All requests excluded charts, balances, provider checkout and invented financial actions. The first mobile candidate's excessive red row buttons prompted a fresh generation before implementation.
