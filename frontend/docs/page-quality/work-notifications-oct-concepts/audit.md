# Staff personal notifications audit

Route `/admin/notifications` is available to STAFF, ADMIN and SUPER_ADMIN for their own account only. Four baseline viewports (430/768/1280/1440) were captured and inspected before changes. The old generic panel has loose full-width filters, large message cards and preferences far below the inbox. It lacks fresh identity preflight for read mutations and loses its uncertainty state on reload. Customer notifications already has compact reusable regions, stale-read guards and persistent recovery.

Current contracts: staff GET notifications supports type/category/unreadOnly/cursor/limit, returns only owned unexpired rows and no total/unread count/search. POST `/:id/read` preserves an existing read timestamp; POST `/read-all` includes unread owned rows outside the current page/filters and expired rows. Neither operation supports unread toggles, deletion or archive. Authentication, staff-role/MFA, CSRF and ownership remain authoritative.

Preference GET/PUT already has optimistic revisions and explicit original-request recovery; see `backend/docs/notification-preference-recovery.md`. Reuse it unchanged. Absent operational pairs default enabled; marketing defaults disabled and requires recorded consent. Security/transactional categories are immutable. Marketing delivery remains unavailable. Recovery may apply an originally unreceived request or return its committed receipt while preserving a later choice. Do not replace this with current-state-only confirmation.

Implementation: extract the accepted customer inbox/preferences regions into a shared account module, keeping the CustomerNotifications entry point and customer visual behavior. Pass the exact account role and role-derived endpoint to each region. Generalize the read guard's fresh identity check with a CUSTOMER default for compatibility. Staff mounts by account/role, renders a dedicated ordered breadcrumb, compact title and two-column layout. New styling is scoped to staff; shared CSS is reused. No new endpoint or schema is required by this page.

Acceptance: fresh desktop/mobile/recovery concepts before runtime changes; seven widths/Axe, four native comparisons, explicit staff/admin/Super Admin ownership/preflight, filters/paging, current-state read recovery, versioned preference recovery and independent stale regions. Run existing customer/personal notification regressions because the regions move. Reuse unchanged backend migration/replay tests; exercise real staff browser/API writes and scoped reads on the established restricted isolated test target with preservation hashes. No application/shared database, provider, migration, backup/restore or deployment operation is part of this gate.

Final integration audit found that workforce-assigned STAFF/ADMIN use a separate shell and API boundary. The current personal-account page gate preserves that restriction. ADM-66 records the remaining workforce notification integration; the connected managed Admin denial is expected, not treated as a passing universal-access check. See the final page report for this scope distinction and evidence.
