# Release blockers and unfinished work

The application is not ready for release against the full supplied brief. This is a historical work list, not a request to waive requirements. The [current completion audit](completion-audit.md) distinguishes current evidence from findings that require revalidation; do not assume every September 17 finding still describes the current source.

## Backend and business decisions

- Vehicle payment requests now expose all four supported purposes with server-authoritative amounts. Customer payment history has no vehicle-transaction filter: the frontend scans cursor pages, retains only matching records and fails closed if it cannot complete the scan (100-page limit). Add an ownership-scoped target filter for accounts with large histories. Target-wide backend advisory locks now serialize intent/attempt creation and settlement across independent keys and vehicle purposes. The 13-case disposable-database suite covers competing creation, legacy duplicate attempts, original-key replay, expiry, vehicle balance calculation and surplus capture accounting. Provider integrations, cross-attempt gateway-ID reuse, complete reconciliation totals and hold resolution still need the wider audit.
- `PaymentsService.createIntent` now checks an actor-bound key and the existing payment owner/purpose/target before evaluating mutable eligibility for a new payment. Reproduction confirmed that a paid order moving to PROCESSING previously broke replay with 404. The revised flow returns the original payment, rejects changed targets with 409 and retains ownership/new-payment checks. Final regression results are recorded in the dashboard handoff. Distinct-key creation is now covered by the target-wide concurrency guard and database regression suite.

- Manual expiry now shares each worker's locked eligibility path. Reproductions confirmed operator paths released reserved inventory/listings during committed payment review/processing and vehicle expiry ignored extended deadlines. Seven order and nine vehicle database cases now pass for protected payment states, unpaid one-time release, deadline rechecks and worker/operator races; audit/history retain operator identity. No financial rule or expiry schedule was changed. Browser bulk expiry remains unavailable: each candidate still commits separately, partial-batch outcome recovery is unresolved, and newly initializing/submitting payments and booking lock ordering require separate verification. The reproduced order/vehicle settlement-versus-expiry stale-read race is now fixed by locking the source before the settlement read; deterministic database tests retain expired sources with exactly one capture and one late-success anomaly, including repeated verification. No real expiry was run.
- Cart clear supports no expected revision or idempotency key. The frontend compares a fresh cart before DELETE and locks unknown outcomes, but another tab can still add/change items between that comparison and deletion. An atomic conditional-delete contract and real concurrent cart/checkout tests remain needed for strict review-to-write guarantees. Clearing the cart does not cancel existing orders or payments.

- Customer care now has 25 endpoint integrations, but real customer ownership, anonymous trusted-origin/rate limiting, staff branch authorization, concurrent status/message/assignment changes and notification delivery remain unverified. Public unlinked submissions do not grant account conversation access, and no linking endpoint is available. Creation/replies lack idempotency keys; uncertain outcomes require record reconciliation. Message refresh is manual, not a live-agent availability promise.

- Promotion management and code preview now have UI coverage, but real administrator/MFA authorization, duplicate-code conflicts, row-lock/version concurrency, customer usage limits and final checkout redemption must be verified against an isolated database. Creation has no idempotency contract; unknown results require record reconciliation. No usage-count/remaining-redemption endpoint or automatic code-less promotion application exists, and the UI does not imply either.

- Product compatibility/image writes use a product advisory lock but accept no expected revision. Child writes do not advance `Product.updatedAt`; frontend preflight compares the actual selected child projection. This reduces stale edits but cannot prevent a race between read and write. Coordinate an atomic expected-revision contract and isolated concurrency tests. Compatibility year validation is resolved: existing database constraints prevented invalid committed ranges, but partial edits produced 500 errors. The service now validates merged bounds inside the product lock and returns 409. Disposable API regression covers invalid partial edits, competing bounds with one winner, nullable ranges and missing children; the underlying constraints are unchanged.

## MFA enrollment authorization correction (verified locally)

The existing-factor enrollment bypass was reproduced against disposable PostgreSQL for CUSTOMER, STAFF, ADMIN and SUPER_ADMIN accounts: pending sessions could prepare TOTP/WebAuthn enrollment. The backend now requires an already MFA-verified session whenever an active factor or unused recovery code exists. First-factor bootstrap remains available otherwise. All four enrollment endpoints enforce this rule, including activation after cryptographic verification.

Account and session row locks serialize the decision. The request's middleware-validated CSRF digest binds it to the current session revision; rotated, revoked, expired and suspended cases are rejected. Activation, recovery-code replacement, audit and session rotation share a transaction. Concurrent bootstrap, final-factor removal and recovery replacement are covered by isolated database regressions. An injected rotation failure preserves the original factor state, codes, session and audit history.

This supersedes the earlier open notes about enrollment authorization, non-atomic enrollment rotation, final-factor removal and concurrent recovery replacement. Password-change concurrency/rotation and single-use sign-in challenge consumption followed by failed rotation still require separate work. Genuine browser-to-API WebAuthn cryptographic verification, physical devices, additional browser engines and deployment RP/origin behavior remain release checks.
