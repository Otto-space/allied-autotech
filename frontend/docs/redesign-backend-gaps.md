# Backend capabilities requiring a separate implementation

The backend and OpenAPI were inspected read-only. These are contract gaps, not disabled working frontend features. Existing backend deployment edits were present before this work and are unrelated.

| Requested capability                                   | Existing contract                                                                                                                                                                                                                  | Missing contract and boundary                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Admin customer directory and customer aggregate detail | `/admin/staff/candidates?email=…` searches eligible staff-promotion candidates by exact email. Operational records carry their authorized customer projections.                                                                    | A dedicated Admin/Super Admin customer list with server-side search, filters, deterministic cursor pagination, permitted sorting and counts; a customer detail projection with explicitly authorized profile, garage, bookings, quotations, orders, payments and support relationships. Ordinary Staff must not gain a general customer directory. These routes do not exist. |
| Customer profile photo                                 | `GET/PATCH /customers/profile` supports personal/contact/address metadata.                                                                                                                                                         | Owner-bound upload preparation, type/size validation, storage token confirmation, image reference in profile response, replacement/removal and old-asset cleanup. Initials are displayed instead.                                                                                                                                                                             |
| Customer garage images                                 | `/customers/vehicles` and `/customers/vehicles/{vehicleId}` support metadata CRUD.                                                                                                                                                 | Owner-scoped image collection, signed upload, confirmation, image identifiers/URLs, alt text, maximum count, order/cover mutation, deletion and storage cleanup. Staff stock is a different resource and cannot be used as a substitute.                                                                                                                                      |
| Service images                                         | Service DTO and administrative service mutations contain no image capability.                                                                                                                                                      | Admin/Super Admin authorized service asset preparation/confirmation, image projection, alt text, replacement/removal, storage cleanup and publication behavior. Service rows use a modest service icon; no invented service photographs.                                                                                                                                      |
| Direct product binary uploads                          | `POST /admin/catalog/products/{productId}/images` and `PATCH/DELETE /admin/catalog/products/{productId}/images/{imageId}` accept approved hosted image metadata: URL, alt text, order and primary selection.                       | Signed upload or backend-mediated binary storage preparation/confirmation bound to the product and authorized administrator. Hosted image CRUD, previews, ordering, primary selection and reviewed removal remain available.                                                                                                                                                  |
| Editing/removing attached stock vehicle images         | `POST /staff/vehicles/{vehicleId}/assets/upload` prepares an upload; `POST /staff/vehicles/{vehicleId}/images` confirms it with alt text, order and primary selection. Public proxy reads use `/public/vehicles/images/{imageId}`. | No PATCH/DELETE image routes are present. Existing images cannot be reordered, have alt text changed, be removed or replaced after attachment through the current contract. A newly attached primary image can replace the primary selection. New mutation routes must retain role, ownership, concurrency and storage checks.                                                |

The reusable uploader supports one validated file at a time, browser/mobile file selection, drag-and-drop, image preview, real progress, cancellation, retry, removal before confirmation and errors. It uses the existing signed flow and storage-host allowlist. No multi-file queue, persistent crop, publish toggle, deletion or maximum image count is fabricated where the server has no contract.

Help articles are local editorial content. Search and category filtering are synchronous; there is no simulated search loading or network-error state. Actual customer-care history, ticket states, enquiries and complaints remain API driven with their existing loading/error/retry handling.

No live backend, payment-provider account, email delivery or object-storage credentials were supplied for this redesign. Browser fixtures validate client behavior and request integrity, not a completed external transaction. A deployment must run the existing real-API suites against its configured services.
